# CRM для заявок из Telegram

**Разработал мини-CRM: клиент заполняет анкету в Telegram, а сотрудник ведёт заявку в браузере — от первого обращения до результата сделки.**

[← Все кейсы](../README.md)

## Задача

Собрать обращения digital-агентства в одной рабочей очереди. Сотруднику нужны карточка клиента, понятная стадия сделки, теги и дата следующего контакта. Заявки из бота и обращения, добавленные вручную после разговора, должны храниться в одной системе.

Проект выполнен как тестовый MVP — первая версия с основными рабочими сценариями.

## Мой вклад

Реализовал веб-приложение и Telegram-бота, общую логику создания заявок, воронку и календарь. Подготовил контейнерное развёртывание, вход сотрудников и защищённый доступ через HTTPS.

## Как работает

1. Клиент проходит анкету в Telegram-боте. Черновик анкеты сохраняется в базе.
2. Бот передаёт ответы в общий сервис создания заявок. Его же использует веб-форма для ручного ввода.
3. Сотрудник открывает карточку, назначает теги, сумму сделки и дату следующего контакта.
4. На канбан-доске перемещает заявку между девятью этапами. Над колонками видит суммы сделок.
5. В календаре проверяет, с кем нужно связаться в выбранный день.

Поиск и фильтры помогают находить обращения по источнику, статусу и тегам.

## Из чего состоит решение

| Компонент | Роль |
| --- | --- |
| Python / Django | Серверная логика, формы, карточки и воронка |
| aiogram / Telegram Bot API | Анкета клиента в мессенджере |
| PostgreSQL | Заявки, этапы, теги и сохранённые черновики |
| Django templates, htmx, Tabler | Браузерный интерфейс и обновление отдельных частей страницы |
| Docker Compose, Gunicorn, WhiteNoise | Запуск веб-приложения, базы и бота |
| Caddy / HTTPS | Защищённое подключение к CRM |

## Технические решения

**Единая логика для двух каналов.** Веб-форма и бот создают обращения через общий сервис. Правила обработки заявки сосредоточены в одном месте.

**Идемпотентность — защита от повторной отправки.** Уникальный идентификатор запроса и учёт обработанных Telegram-сообщений помогают не создавать второй лид из повторного события.

**Сохранение состояния.** Черновик анкеты хранится в базе, а не только в памяти процесса бота.

**Управляемый доступ.** Вход сотрудников работает через сессии Django. Предусмотрены защита CSRF — от поддельных запросов с чужих страниц — и ограничение попыток входа.

## Проверка и результат

MVP развёрнут: проверены HTTPS, вход, страницы CRM, миграции PostgreSQL и сохранность данных после перезапуска. В локальном прогоне прошли 25 тестов Django на SQLite. Полный набор тестов на PostgreSQL и реальный путь пользователя от анкеты Telegram до карточки заявки на момент фиксации результата ещё ожидали проверки.

Получилась единая система для приёма и ведения обращений с воронкой, календарём и учётом сумм. Интеграция с личным Telegram-аккаунтом оставалась следующим этапом.

**Статус:** реализованный и развёрнутый тестовый MVP.
